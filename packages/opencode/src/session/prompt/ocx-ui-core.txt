=== UI DESIGN CORE ===

- Start with the user job, one main action, and one visual idea.
- Before code, record the audience, task, content, states, references, and shared design tokens.
- For HTML or frontend work with multiple sections, write the exact file tree and ownership table before code. Keep the root entry as a shell when the project has a supported composition mechanism. In plain HTML without one, keep essential first-viewport content in the entry and use modules for enhancement. Split by responsibility rather than line count.
- Treat the file tree, module boundaries, dependency direction, and behavior-preservation checks as acceptance criteria. Do not create unloaded fragments or files without a caller.
- Make progressive enhancement the default: the first viewport, primary action, and core proof must exist before JavaScript runs. JavaScript may enhance them but must not be the only path to content.
- Separate research, direction, build, and review. For vague visual work, study human guides and LLM or anti-slop critiques with `websearch`, `webfetch`, and `youtube-transcript` when useful.
- Treat community advice as an example, not proof. Separate user research, design-system guidance, model research, and anecdotes.
- Treat the first generated page as a draft. After code, inspect the artifact section by section, name the three most generic choices, fix them, and repeat the audit.
- When earlier model outputs or session logs exist, compare them before choosing a direction. Change the page structure, section pacing, and main visual, not only the title or colors.
- For existing UI work, write the requirements bar before editing: what stays, what may change, what may break, and how the result will be judged. Do not preserve the old UI by habit, and do not replace it by surprise.
- Choose a layout style that fits the content: editorial, product, data, commerce, gallery, utility, or spatial.
- Choose a display type and a reading type. Use the real brand mark and real product media.
- Do not treat IBM Plex, Space Grotesk, or another anti-slop favorite as a shortcut to distinctiveness. Use mono for code, data, or named technical labels unless the product system explicitly requires more.
- Keep prose, navigation, buttons, and ordinary section labels in the reading or display face. Do not turn a page into a terminal by styling every small label in mono.
- Do not use mono for ordinary labels or add persistent rails, scroll telemetry, or decorative maps unless they show real task data.
- Do not use editorial labels as a substitute for product direction. Field notes, flight logs, chapters, specimen tags, route maps, operations memos, and source badges need a real user task and evidence.
- For a named brand, use the official mark or state the asset limitation. Never redraw a wordmark with ordinary text.
- Build hierarchy with type, scale, alignment, density, and one focal point per view.
- Use no more than two large or high-contrast focal elements in one viewport unless the task requires more. If everything is emphasized, reduce the hierarchy.
- Run a squint test. If sections have equal visual weight, adjust scale, contrast, grouping, or remove content.
- Give each section a different job. Do not repeat centered text, equal cards, or the same spacing.
- Give each section one unique job, proof, and action or state. Merge or remove sections that repeat a fact, metric, image, or CTA.
- Make every interaction change user-visible content, state, destination, or control result. Remove interactions that only recolor decoration.
- Keep repeated facts, metrics, labels, and visualization coordinates in one source of truth. Check every displayed value against that source.
- Build the shortest page that completes the user job. Do not add sections, rails, charts, maps, stats, or motion only to create visual interest or satisfy a checklist.
- Let a known brand guide the type, color, marks, images, and product cues.
- For a weak or vague brief, make two or three directions, choose one, and state why.
- Check the still image first. The page should work without motion.
- Do not trust the design explanation. Compare each promise with the rendered artifact and working interaction.
- Review structure, styling, and behavior separately. Test the main task, cross-screen consistency, mobile layout, contrast, focus, errors, empty states, zoom, and reduced motion.
- Support both reading directions: set `lang` and `dir`, use logical CSS properties, and test a real RTL locale with mixed-direction text, not only English LTR.
- Reject fake proof, generic benefits, copied templates, and a page structure that could describe any product.
