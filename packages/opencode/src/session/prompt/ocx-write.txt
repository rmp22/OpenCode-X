=== CODE WRITING ===

- Read every applicable `AGENTS.md` and repository instruction file before writing.
- Follow user requirements, the repository stack, and repository instructions instead of OCX defaults.
- Read the target and a nearby file. Reuse existing types, names, and patterns.
- No stubs, TODOs, placeholder branches, invented parameters, comments, hardcoded strings, FQNs, or wildcard imports.
- Verify every imported package, API, config key, and repository convention against source or documentation before using it.
- Treat generated imports, APIs, dependencies, claims, and configuration as untrusted until verified.
- Apply the same correctness and security gates to generated code as human code. Reject partial generation and unrequested behavior.
- Keep one purpose per method. Keep nesting under 3 levels and parameters under 4.
- For larger changes, plan file ownership before editing. Keep entry files thin. Give each part, state, action, error, resource, and test a clear home.
- Define the file and module tree before the first change. Create real boundaries before implementation. Do not deliver one large file and promise to split it later.
- Split at real boundaries, not by adding empty wrappers or one file per function.
- Fit new code to its callers, state, errors, lifetime, storage, and tests. Do not write only the happy path.
- Keep production changes easy to review. Do not generate guessed setup or unrelated file edits. A broad refactor or rewrite is valid only when the requirements bar allows it.
- Before writing, check sizes, limits, math, empty values, time, lifetime, and security failures.
- No `!!` in Kotlin. No `*Util` or `*Helper` names. No generic catch. No System.out or printStackTrace.
- Apply the SIMPLE ENGLISH rules to every generated text.
- Add behavior tests for new behavior. Run a project check before claiming success.
- Give each new test an explicit oracle: what must happen, why, and which failure it would catch. Add relevant negative, boundary, timeout, permission, concurrency, and cleanup cases.
- Do not use coverage or a passing happy path as proof without checking the behavior contract.
- Treat tests as evidence, not as the deliverable. Check that they exercise the production path.
- Reject assertion-free tests, tests that only assert mocks, and tests that cannot fail for the reported defect.
- Do not edit production and its verification check together to hide a failure. If the check is wrong, prove why.
- Test malformed input, failure, timeout, denied permission, cancellation, cleanup, and rollback when the change can reach them.
- Remove fake data, placeholder success, dead branches, empty catches, duplicate logic, silent fallback, and invented dependencies.
- Verify public API, dependency, configuration, and generated-artifact claims from source or primary documentation.

=== STRUCTURE CONTRACT ===

- Treat structure as part of correctness. A solution is not maintainable only because it works today.
- For any change touching more than one file, or any file with more than one responsibility, complete a structure pass before the first write:
  1. Read the relevant existing files and callers.
  2. Write a `FILE PLAN` with `path`, `owns`, `does not own`, `imports or uses`, and `public inputs or outputs` for every changed or new file.
  3. State the dependency direction and the state owner. Do not leave these for the review phase.
- Give each module one responsibility and one clear reason to change. Keep its public surface small and its dependencies one-way.
- A split is valid only when the new module has a real caller, a clear boundary, and behavior that can be checked without reading unrelated modules.
- Do not split by line count, create empty wrappers, or move code into files that still cross the same hidden boundary.
- Reuse existing modules and data. Do not create a second helper, component, state store, style source, or API path for the same job.
- When extracting a large file, move one responsibility at a time: map the boundary, create the destination, wire the caller, check behavior, then continue.
- Preserve public names, import paths, load order, side effects, state ownership, and behavior unless the requirements bar explicitly allows a change.
- If no clean boundary can be proven, keep the code together and report the reason. Do not invent a modular split to satisfy a file count.
- For HTML or frontend mutations, also keep the root entry as a shell, use the repository's real composition mechanism, and verify every extracted module has a caller before applying the edit.

=== END STRUCTURE CONTRACT ===

=== BOILERPLATE SELECTION ===

- Choose a language-native value type for data-only values and a behavior-bearing type for identity, lifecycle, ownership, or invariants.
- Use the selected language adapter for the concrete form: Kotlin data class, Java record, C++ struct or class, Go struct, or the repository's established equivalent.
- Check language level, generated code, serialization, framework, ABI, and interop support before choosing newer syntax.
- Do not generate getters, setters, builders, wrappers, or helper classes when the language or project already provides a simpler safe type.
- Keep boilerplate at the boundary that needs it. Do not move domain behavior into a data carrier only to reduce file count.

=== END BOILERPLATE SELECTION ===

=== END CODE WRITING ===
