=== COMPOSE ADAPTER ===

- Treat Compose as its own stack. Combine this adapter with `kotlin`, `android`, or another platform adapter when needed.
- First identify the targets: Android-only Jetpack Compose, Compose Multiplatform, or shared logic with native platform UI.
- Read the Gradle modules and source-set graph before editing. Preserve the repository's existing Android, iOS, desktop, web, or native targets.
- Keep shared code in `commonMain` only when every target can compile it. Put platform APIs and dependencies in the correct platform source set.
- Use intermediate source sets when several targets share an API. Do not copy the same implementation across platform folders without checking the source-set hierarchy.
- Keep composables focused on rendering and events. Hoist state to the lowest common owner that reads and writes it.
- Expose immutable UI state and explicit events. Keep business state in the screen state holder or ViewModel when the product architecture uses one.
- Represent screen UI state with a data class or sealed hierarchy when that matches the state model. Do not use a data class for a long-lived owner with identity or side effects.
- Keep local UI state close to the composable. Do not hoist it only because a ViewModel exists.
- Use lifecycle-aware collection and structured coroutine scopes. Cancel work when the screen or composition leaves its lifecycle.
- Keep platform-specific behavior behind interfaces, source-set boundaries, or explicit expect and actual declarations.
- Use semantics, content descriptions, test tags only when needed, stable keys, and predictable focus order.
- Test recomposition, configuration or lifecycle changes, loading, empty, error, retry, cancellation, large text, touch, keyboard, and accessibility states.
- Test shared behavior in common tests and platform behavior in platform tests. Do not claim cross-platform support after Android-only tests.
- Use previews as a development aid, not as proof that runtime state, navigation, or platform behavior works.
- When AOSP or Google guidance conflicts with a product or target platform, preserve the stronger user, accessibility, compatibility, and security requirement and record the tradeoff.
